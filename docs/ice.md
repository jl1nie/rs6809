# ICE（インサーキット・エミュレータ）とOS-9モニタ

エミュレータ内部にICE相当のデバッグ機能を持たせ、ブラウザのGUIから操作します。
同じ画面でNitrOS-9のシステムコール（プリミティブ）、プロセス、スケジューラ、モジュール、メモリを観察できます。
外部crateは使わず、標準ライブラリのHTTPサーバーと1枚のHTML（`src/ice/ui.html`）で構成しています。

## 起動

```sh
sh examples/nitros9-ice.sh                 # Level 1、http://127.0.0.1:6809/
sh examples/nitros9-level2.sh --ice        # Level 2（ディスク構築後）
sh examples/nitros9-ice.sh 127.0.0.1:8080  # 待ち受けアドレスを変更
```

`--ice [アドレス]` を付けると、通常の実行ループの代わりにICEが動きます。既定の待ち受けは `127.0.0.1:6809` です。
`--ice-halt` を付けるとリセット直後で停止した状態から始まります。`--boot` と `--script` の自動入力は従来どおり使えます。
`--until`・`--max-cycles`・`--measure-from` とは同時に使えません。

コンソール（ACIA 1、`/term`）はブラウザ右側の端末に出ます。端末をクリックするとキー入力がそのままゲストへ送られます。
下の入力欄は1行をCR付きで送ります。Telnetモード（`--telnet`）と併用すると、追加ACIAはTelnet側で、ACIA 1はブラウザでも見えます。

## 構成

```text
 ブラウザ (ui.html)  ──HTTP/JSON──  HTTPスレッド群 (ice/http.rs)
                                        │ mpsc（要求ごとに返信チャネル）
                                        ▼
                         エミュレータスレッド (ice/mod.rs: Ice)
                          ├ Cpu / Machine（所有）
                          ├ 実行制御・ブレーク判定・命令トレース
                          ├ disasm.rs   6809逆アセンブラ（OS9 F$xxx表記）
                          └ os9.rs      OS-9構造の読み取り・システムコール追跡
```

- CPUとマシンはエミュレータスレッドだけが持ちます。HTTPスレッドは要求をチャネルで渡すので、表示は常に命令境界の一貫した状態です。
- 実行中は約8ms単位で命令を実行し、その合間に要求を処理します。停止中は要求を待ちます。
- デバッガの読み出しは `Machine::peek` を使います。ACIAの受信データを取り出すなどのI/O副作用を起こしません。
  書き込み（`poke`）はRAMだけで、デバイスレジスタには届きません。
- `Machine::step` から時計の進行を `Machine::tick` として分離しました。通常実行の経路は従来と同じです。

## ICE機能

| 機能 | 内容 |
|---|---|
| 実行・停止 | F5／F6。速度上限（1kHz〜10MHz、最大）を選べ、遅くするとOS-9の動きを目で追えます |
| ステップ | F11で1命令。割り込みが受け付けられる場合はベクタへの分岐が1ステップです |
| ステップオーバー | F10。`JSR`・`BSR`・`LBSR`・`SWI`・`OS9` を1命令として実行し、同じプロセスでSが戻った時点で停止 |
| ステップアウト | Shift+F11。`RTS`・`RTI`・`PULS PC` でSが現在より上に戻った時点で停止 |
| その行まで実行 | 逆アセンブルの行をダブルクリック |
| ブレークポイント | PC一致。64KBのビット表で判定し、再開時は現在PCを1回だけ飛ばします |
| ウォッチポイント | CPU論理アドレスの範囲に対する読み・書き・両方。該当命令の実行完了後に停止します |
| レジスタ・メモリ編集 | 停止中にレジスタ値やメモリのバイトをクリックして変更 |
| メモリ表示 | CPU論理空間、OS-9システム空間、物理RAM先頭64KB |
| MMU表示 | 2組のタスクマップ（各8バンク）、実行中のタスク、書き込み保護、固定上位領域 |
| 実行トレース | 直近4096命令のレジスタと命令バイト。表示時に逆アセンブルします |

## OS-9連携の仕組み

### システムコールの捕捉

OS-9のサービス要求は `SWI2` の直後に1バイトの機能コードを置く形です（`OS9 F$Fork` = `10 3F 03`）。

1. 命令を実行する前に、PCの命令が `10 3F` なら呼び出しとして記録します。
   このとき呼び出し元の空間でレジスタと引数（パス名、書き込むデータ、モジュール名など）を読みます。
2. カーネルはスタック上のPCを機能コードの次へ進めてから `RTI` で戻ります。
   そこで「PC＝呼び出し位置+3、S＝呼び出し時と同じ、同じプロセス（`D.Proc` のID）」になった時点を復帰とみなし、
   出力レジスタとCCのキャリー（エラー）・Bのエラー番号を記録します。
3. 呼び出し時に同じプロセスの未完了の呼び出しがあれば、それを親とします。
   これにより、ユーザーの `I$ReadLn` の内部でドライバが行う `F$Sleep`、その中の `F$NProc` などを木構造で表示できます。
4. `F$Exit`・`F$Chain`・`F$NProc` は戻らない呼び出しとして扱います。ユーザー状態から新しい呼び出しが来た時点で、
   そのプロセスに残っていた未完了の呼び出しは破棄します（ユーザー状態のプロセスはカーネル呼び出しの途中にはないため）。
5. `I$Open`・`I$Create` の結果からパス番号とパス名の対応を学習し、`I$Dup`・`I$Close`・`F$Fork`（標準パスの継承）で更新します。
   以後の `I$Write` などは「パス1(stdout)」「パス3(echo)」のように表示されます。

システム状態（カーネル・ドライバ内部）の呼び出しは1秒に数十万回発生するため、レジスタの文字列化を表示時まで遅らせます。
ユーザー呼び出しとシステム呼び出しは別々に保持し（それぞれ最新15,000件・60,000件）、内部呼び出しが多くても
処理中のユーザー呼び出しが押し出されないようにしています。

### カーネル構造の読み取り

オフセットは参照キットの `defs/os9.d` に従います。サービス名・エラー名・`SS.xxx` は
同ファイルからLevel条件を評価して生成した `src/ice/tables.rs` を使います。

| 項目 | Level 1 | Level 2 |
|---|---|---|
| 判定 | `D.Init`($2A)が `Init` モジュールを指す | `D.Init`($24)が `Init` モジュールを指す |
| システム空間 | 64KB平坦 | ブロック0は物理0、その他は `D.SysDAT` のDATイメージ |
| 実行中プロセス | `D.Proc`($4B) | `D.Proc`($50) |
| キュー | `D.AProcQ`/`D.WProcQ`/`D.SProcQ`（$4D/$4F/$51） | 同（$52/$54/$56） |
| プロセス表 | `D.PrcDBT` のページ表、64バイト記述子 | `D.PrcDBT[ID]` が512バイト記述子の上位バイト |
| モジュール | `D.ModDir` の4バイト項目 | `D.ModDir`〜`D.ModEnd`($58)の8バイト項目、モジュールのDATイメージ経由で読む |
| メモリ | `D.FMBM` の256バイト単位ビットマップ | `D.BlkMap` の8KBブロックフラグ |

MulticompのLevel 1カーネルもMMUを有効（恒等マップ）にするため、MMUの状態ではなく `Init` モジュールの位置でLevelを判定します。

### 画面（OS-9モニタ）

- **スケジューラ**：`D.Proc` とアクティブ・待機・睡眠キュー。下のタイムラインは `D.Proc` の変化から求めた実行区間と、ユーザーのシステムコール（▲）です。
- **プロセス**：親子関係を木で表示し、`P$State` のフラグ（Sys・TSlp・TOut・Susp・Cond・Dead）、キュー、優先度、エージ、パス表、Level 2ではDATイメージを示します。
- **システムコール**：番号・プロセス・名前・引数・結果・所要サイクル。実行中の呼び出しは「実行中…」と表示します。
  行を選ぶと、そのプリミティブがカーネル内で何をするかの説明、入出力レジスタの差分、カーネル内部の呼び出しの木を表示します。
  そこから「この呼び出しで停止」「復帰で停止」を設定できます。
- **ブレーク条件**：特定のサービスの呼び出し前・復帰後、エラー復帰、プロセス切り替え、対象プロセスIDでの絞り込み。記録自体も切り替えられます。
- **モジュールディレクトリ**、**メモリマップ**（モジュール・プロセス記述子・使用中・空きを色分け）。

## 使い方の例

`echo hello` を実行すると、システムコールの一覧に次の流れが現れます（Level 1、プロセス2がShell）。

```text
P2 F$PrsNam   "echo"                 → 長さB=4
P2 F$Link     X→"echo"               → エラー E$MNF   メモリにないので
P2 I$Open     "echo"                 → パス番号A=3    実行ディレクトリのファイルを開き
P2 I$Read     パス3(echo) 最大13バイト → "\x87\xCD…"   モジュールヘッダを確認
P2 F$Load     X→"echo"               → ヘッダU=$B700  読み込んで登録
P2 F$Fork     モジュール"echo" パラメータ"hello\r" → 子プロセスID=3
P3 I$WritLn   パス1(stdout) 6バイト "hello\r"
P3 F$Exit     終了ステータスB=0       (戻らない)
P2 F$Wait     → 子3が終了 ステータス0
```

- `F$Fork` の呼び出しで停止させ、ステップオーバーするとプロセス3が作られ、スケジューラ表示とプロセス表が変わる様子を確認できます。
- 「エラーで復帰したら停止」を有効にして `echo hi` を実行すると、まずShellの `F$PrsNam` が名前の終わりで `E$BNam` を返した直後に止まります。
  再開すると、メモリにない `echo` の `F$Link` が `E$MNF` を返した直後に止まります。OS-9ではエラー復帰も通常の制御の流れであることがわかります。
- 「ユーザー呼び出しのみ」を外すと、`I$ReadLn` の待ち時間にドライバが `F$Sleep` を繰り返し、カーネルが `F$NProc` で
  次のプロセスへ切り替え、時計割り込みで `F$AProc` によりアクティブキューへ戻す様子が見えます。
- 速度を1MHz（実機相当）以下にすると、タイムラインでプロセスの切り替えを目で追えます。

## HTTP API

すべて `127.0.0.1` 上のJSONです。数値の既定は10進、アドレスは16進です（`$`・`0x` も可）。

| パス | 内容 |
|---|---|
| `GET /api/state` | 実行状態、停止理由、レジスタ、MMU、ブレーク設定、OS-9の要約 |
| `POST /api/run` `pause` `step?n=` `over` `out` `runto?addr=` `speed?hz=` | 実行制御 |
| `POST /api/reg?name=&val=` | レジスタ変更 |
| `POST /api/bp?addr=&op=add\|del\|toggle\|clear` | ブレークポイント |
| `POST /api/watch?addr=&len=&kind=r\|w\|rw`、`op=del&index=`、`op=clear` | ウォッチポイント |
| `GET /api/disasm?addr=&n=&back=` | 逆アセンブル（`back` で手前の命令境界から） |
| `GET /api/mem?addr=&len=&space=cpu\|sys\|phys\|pidN`、`POST ...&val=16進` | メモリ |
| `GET /api/trace?n=` | 実行トレース |
| `GET /api/console?since=`、`POST /api/console`（本文をACIA 1へ） | コンソール |
| `POST /api/os9break?code=&when=call\|return&op=del`、`errors=` `switch=` `pid=` `trace=` | OS-9ブレーク条件 |
| `GET /api/os9/procs` `modules` `memmap` `services` | OS-9構造 |
| `GET /api/os9/calls?since=&user=1&pid=&parent=&limit=` | システムコール（`since` は更新番号） |

テストやスクリプトからは `Ice::command("GET", "/api/state", b"")` で同じAPIを直接呼べます。

## 検証

```sh
cargo test --release --test ice
cargo test --release --test ice -- --ignored   # 参照キットのLevel 1・構築したLevel 2ディスク
```

`--ignored` のLevel 2テストには `python3 scripts/build-level2-disk.py` で構築したディスクが必要です。

- 逆アセンブラ、ステップオーバー／アウト、ブレークポイント、ウォッチポイント、メモリ・レジスタ操作。
- 最小のLevel 1構造と、スタック上のPCを進めて `RTI` するカーネル相当のハンドラを置き、
  `I$WritLn` の呼び出し前停止・復帰後停止・引数と結果の表示を確認します。
- 参照キットのNitrOS-9 Level 1を起動し、`echo traced` の `F$Fork` と子プロセスの `I$WritLn`、Shell・SysGoのプロセス表を確認します。
- Level 2は `os9.d` の定義どおりに配置した合成メモリで、システムDATを通じた読み出し、プロセス記述子・DATイメージ、
  モジュールディレクトリ、ブロックマップの解釈を確認します。
- 構築したLevel 2ディスクを起動し、startupの `echo` を `F$Fork` した復帰時点で停止して、
  SysGo→Shell→Shell→Echoのプロセス木、実行中プロセスのタスク番号、子のアクティブキュー、システムプロセスとシステムDAT、
  Krnの位置（ブロック7のオフセット$1000）、各モジュールが占めるブロック、ブロックマップの使用中フラグを確認します。

## 制約と注意

- Level 2のモジュールのアドレス（`MD$MPtr`）はモジュールのDATイメージ内の位置です。画面では物理アドレスに換算して表示し、元の値はツールチップに出します。
- Level 2の `P$UTicks` などのカウンタは、このカーネルが更新しないため表示しません（システムプロセスでは同じ位置にスタックの内容が残ります）。
- Level 2のタスク番号はプロセスが動いている間だけ割り当てられます。待機中・睡眠中のプロセスは0（未割り当て）です。
- 停止した時点が `F$NProc` の途中だと、実行待ちのプロセスがどのキューにも載っていないことがあります。
  決まった時点で見るには、OS-9ブレーク条件（呼び出し・復帰）で止めてください。
- 記録を有効にすると、シェル待機中で約42MHz相当（記録なしで約87MHz相当、通常実行は数百MHz相当）になります。実機の数十倍の速度です。
- ウォッチポイントはCPU論理アドレスで判定します。Level 2で別プロセスの同じ論理アドレスにも反応します。プロセスIDでの絞り込みはOS-9ブレーク条件のみです。
- 待ち受けは既定でlocalhostのみ、認証はありません。外部に公開しないでください。
- 停止中もタイマーは進みません（命令単位で時計を進めるため）。ステップ実行中に時計割り込みが入るのは正しい動作です。

## 今後の拡張（検討）

- LWASMのリストやマップファイルからシンボルを読み込み、逆アセンブルとスタックにラベルを付ける。Cでは `c.asm` 出力と行番号の対応。
- 条件付きブレークポイント（レジスタ・メモリの式）、通過回数、ログ出力のみのトレースポイント。
- プロセスごと・モジュールごとのサイクルプロファイル。
- スナップショットと逆実行（一定間隔の状態保存と命令トレースによる巻き戻し）。
- Debug Adapter Protocol に対応し、VS Codeなどのエディタからも同じICEを操作する。
- Level 2でタスクごとのMMUマップとプロセスのDATイメージを対応付けて表示する。
