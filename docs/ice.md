# ICE（インサーキット・エミュレータ）とOS-9モニタ

エミュレータ内部にICE相当のデバッグ機能を持たせ、ブラウザのGUIと、Debug Adapter Protocol（DAP）経由のエディタ（VS Codeなど）から操作します。
同じ画面でNitrOS-9のシステムコール（プリミティブ）、プロセス、スケジューラ、モジュール、メモリを観察できます。
外部crateは使わず、標準ライブラリのHTTP・DAPサーバーと1枚のHTML（`src/ice/ui.html`）で構成しています。
LWASM・Microware RMAのリストとリンクマップを読み込むと、逆アセンブルとスタックにシンボルを付け、Cやアセンブリのソース行単位でブレーク・ステップできます。

## 起動

```sh
sh examples/nitros9-ice.sh                 # Level 1、http://127.0.0.1:6809/
sh examples/nitros9-level2.sh --ice        # Level 2（ディスク構築後）
sh examples/nitros9-ice.sh 127.0.0.1:8080  # 待ち受けアドレスを変更
```

`--ice [アドレス]` を付けると、通常の実行ループの代わりにICEが動きます。既定の待ち受けは `127.0.0.1:6809` です。
`--ice-halt` を付けるとリセット直後で停止した状態から始まります。`--boot` と `--script` の自動入力は従来どおり使えます。
`--until`・`--max-cycles`・`--measure-from` とは同時に使えません。

コンソール（ACIA 1、`/term`）はブラウザ右側の端末に出ます。端末をクリックするとキー入力がそのままゲストへ送られます。
下の入力欄は1行をCR付きで送ります。Telnetモード（`--telnet`）と併用すると、追加ACIAはTelnet側で、ACIA 1はブラウザでも見えます。

## 構成

```text
 ブラウザ (ui.html)  ──HTTP/JSON──  HTTPスレッド群 (ice/http.rs)
 VS Code など        ──DAP/TCP───  DAPスレッド群  (ice/dap.rs)
                                        │ mpsc（Inbox：HTTP要求・DAPメッセージ）
                                        ▼
                         エミュレータスレッド (ice/mod.rs: Ice)
                          ├ Cpu / Machine（所有）
                          ├ 実行制御・ブレーク判定・命令トレース
                          ├ disasm.rs   6809逆アセンブラ（OS9 F$xxx表記）
                          ├ osmon.rs    OSの差し替え口（OsMonitor）とシステムコールの記録
                          ├ os9.rs      NitrOS-9の実装（構造の読み取り・説明文）
                          ├ symbols.rs  リスト・マップの読み込み、モジュール位置への配置
                          └ dap.rs      DAPの要求処理とイベント（停止・出力）
```

- CPUとマシンはエミュレータスレッドだけが持ちます。HTTPスレッドは要求をチャネルで渡すので、表示は常に命令境界の一貫した状態です。
- 実行中は約8ms単位で命令を実行し、その合間に要求を処理します。停止中は要求を待ちます。
- デバッガの読み出しは `Machine::peek` を使います。ACIAの受信データを取り出すなどのI/O副作用を起こしません。
  書き込み（`poke`）はRAMだけで、デバイスレジスタには届きません。
- `Machine::step` から時計の進行を `Machine::tick` として分離しました。通常実行の経路は従来と同じです。

## ICE機能

| 機能 | 内容 |
|---|---|
| 実行・停止 | F5／F6。速度上限（1kHz〜10MHz、最大）を選べ、遅くするとOS-9の動きを目で追えます |
| ステップ | F11で1命令。割り込みが受け付けられる場合はベクタへの分岐が1ステップです |
| ステップオーバー | F10。`JSR`・`BSR`・`LBSR`・`SWI`・`OS9` を1命令として実行し、同じプロセスでSが戻った時点で停止 |
| ステップアウト | Shift+F11。`RTS`・`RTI`・`PULS PC` でSが現在より上に戻った時点で停止 |
| その行まで実行 | 逆アセンブルの行をダブルクリック |
| ブレークポイント | PC一致。64KBのビット表で判定し、再開時は現在PCを1回だけ飛ばします |
| ウォッチポイント | CPU論理アドレスの範囲に対する読み・書き・両方。該当命令の実行完了後に停止します |
| レジスタ・メモリ編集 | 停止中にレジスタ値やメモリのバイトをクリックして変更 |
| メモリ表示 | CPU論理空間、OS-9システム空間、物理RAM先頭64KB |
| MMU表示 | 2組のタスクマップ（各8バンク）、実行中のタスク、書き込み保護、固定上位領域 |
| 実行トレース | 直近4096命令のレジスタと命令バイト。表示時に逆アセンブルします |
| シンボル | 逆アセンブルにラベル行・ソース行・分岐先の名前（`LBSR $AA0E <_stkcheck>`）を表示。移動欄にシンボル名を入力可 |
| ソース行・シンボルのブレーク | `sum`、`hello.c:19` のように指定。モジュールがロードされた位置に自動で配置し直します |
| スタック | Sから32語。呼び出し命令の直後を指す値を戻り番地（↩）として示し、シンボルを付けます |

## シンボルとソース行

```sh
rs6809 --rom ... --disk ... --boot --ice --symbols artifacts/level2/echo.lst --symbols artifacts/cdebug/hello --source-dir examples
```

`--symbols` は繰り返し指定でき、ファイルかディレクトリ（中の `.lst` と、対応する `.lst` がない `.map`）を読み込みます。
ブラウザの「シンボル」欄やDAPの `attach` からも読み込めます。

| 入力 | 内容 |
|---|---|
| LWASMのリスト（`lwasm --list`） | ラベル、各行のコード範囲、ソース本文。先頭が `$87CD` のモジュールはモジュール内オフセットとして扱います |
| LWLINKのマップ（`Symbol: 名前 (ファイル) = XXXX`） | 絶対アドレスのシンボル |
| Microware RMAのリスト（`c.asm -l`）＋同名の `.map`（`c.link -m -s`）＋ `.m`（`c.prep -l`） | Cの関数シンボル、命令ごとのモジュール内オフセットとCの行 |

- `ファイル@モジュール名` でLWLINKのマップやリストをそのモジュールに配置し、`ファイル@abs` で絶対アドレスとして扱います。
- OS-9のモジュールは位置独立で、ロードされる場所は実行ごとに変わります。モジュール内オフセットの表は、
  モジュールディレクトリで同名のモジュールを探し、その**物理RAMの範囲**に配置します。
  Level 1では論理アドレスそのまま、Level 2ではモジュールのDATイメージのブロックから物理アドレスを求めるため、
  同じ表がどのプロセス空間で実行されても使えます。配置は `F$Link`・`F$Load`・`F$Fork`・`F$Chain`・`F$UnLink`・
  `F$Exit` などの復帰時、プロセス切り替え時、停止・再開時に更新します。
- ソース行やシンボルのブレークポイントは、モジュール内オフセットを物理アドレスに変換したビット表で判定します。
  モジュールのロード前に設定しておくと、ロードされた時点で有効になります（コードを実行する前に配置されます）。
- LWASMのリストのファイル名は左が切り詰められる（`s/source-echo.asm`）ため、リストのディレクトリ、その1階層下、
  `--source-dir` で末尾一致するファイルを探します。見つからない場合もリスト内の本文でソースを表示します。
- 局所ラベル（`l@`、Cコンパイラの `_3` など）は、その番地ちょうどのときだけ表示し、「名前+オフセット」の基準には大域ラベルを使います。

### Cのソースレベルデバッグ

Microware Cの `.a` には通常、行番号の情報がありません。`c.prep -l` を使うと、前処理器が各ソース行を
`* *` で始まるコメントとしてアセンブリへ残し、`.m` に「ファイル名（`#7`）・ソース行（`#6`）」の記録を出します。
RMAのリスト（`c.asm -l`）には各命令のセクション内オフセットと、そのコメントが同じ順に並び、
`c.link -m -s` のマップがセクション（`hello_c`）のモジュール内位置と関数シンボルを与えます。
この3つを突き合わせ、各命令を直前のソース行に対応付けます。

```sh
python3 scripts/build-c-disk.py            # 初回のみ（Level 2は build-level2-disk.py）
python3 scripts/c-debug-build.py examples/hello.c            # Level 1のC開発用ディスク
python3 scripts/c-debug-build.py examples/hello.c --level2 --out artifacts/cdebug/level2-hello
```

スクリプトはホストのCファイルをディスクの `/dd/SOURCES` へ書き込み、エミュレータでゲストを起動して

```text
c.prep -l hello.c >hello.m → c.pass1 → c.pass2 → c.asm hello.a -l >hello.lst → c.link ... -m -s >hello.map
```

を実行し、`hello.lst`・`hello.map`・`hello.m` を `artifacts/cdebug/hello/` へ取り出します。
実行ファイルは `/dd/SOURCES/hello` です。行とコードの対応を保つため最適化（`c.opt`）は通しません。
ディスクイメージに書き込むので、同じイメージを使うエミュレータは止めてから実行してください。

```sh
./target/release/rs6809 --rom reference/nitros9-basic09-starter-kit/nitros9-runtime/6809M.bin \
  --disk artifacts/ccompiler/multicomp09-c.img --boot \
  --dap --symbols artifacts/cdebug/hello --source-dir examples
```

ゲストで `/dd/SOURCES/hello` を実行すると、`hello.c:19` などのブレークポイントで止まり、
行単位のステップオーバー・ステップイン（`sum` の `{` へ）・ステップアウトができます。

- 行単位のステップは、同じプロセス・同じMMUタスクで別の行の命令に来た時点で止まります。
  ステップオーバーでは深いフレーム（Sが開始時より下）を飛ばし、行情報のないライブラリ（`printf` など）は中に止まりません。
  デバッグ対象のコードの `RTS`/`PULS PC` で呼び出し元の行情報のないコード（`_cstart`）へ戻った場合も止まります。
- 関数の後始末（`leas`・`puls u,pc`）は最後の文の行に含まれます。`fcc` などの定数は行に対応付けません。

### Cの変数

ブレークポイントで止まると、引数・ローカル変数・`static` 変数・大域変数を型に応じて表示します（ブラウザの「変数」欄、DAPの「ローカル」「大域」スコープ）。
呼び出し元のフレームを選ぶと、そのフレームの変数も見られます。構造体・配列・ポインタの指す先は展開でき、
`char *` と `char` の配列は文字列として表示します。DAPの `evaluate`（ウォッチ・ホバー・デバッグコンソール）では
`n`、`s.x`、`p->next->val`、`arr[1]`、`*p` の形の式を使え、変数一覧から整数・文字・ポインタの値を書き換えられます。

構成は次の3つに分けています。コンパイラ固有なのは3だけです。

| 部分 | ファイル | 内容 |
|---|---|---|
| 1. 変数の記述と表示 | `debuginfo.rs` | 型、位置（フレーム相対・レジスタ・データ基準相対・絶対）、フレームの規則（各命令でのフレーム基準、戻り番地と退避レジスタの位置）、値の書式、式の評価 |
| 2. C宣言の解析 | `cdecl.rs` | 前処理済みのソース（`.m` に含まれる）から大域変数・関数・引数・ブロックごとのローカル変数・構造体・typedefを取り出す。K&R形式と簡単なANSI形式 |
| 3. Microware C用アダプタ | `microware.rs` | 下の配置規則で1の記述を作る |

Microware Cは記号表を残さないため、配置の規則を検証用プログラムのコンパイル結果から確かめて実装しています。

- プロローグの `pshs u` の直後のSをフレーム基準Fとします。戻り番地はF+2、呼び出し元のU（レジスタ変数）はF+0です。
- 引数はF+4から順に置かれます。`char`・`int`・ポインタは2バイト（`char` は下位バイト）、`long` は4バイト、`double` は8バイトです。
- ローカル変数は宣言順に、Fの下へ隙間なく置かれます。ブロック内の変数は外側の変数のさらに下に置かれ、並んだブロックは同じ位置を使い回します。
- `register` のうち、`int` かポインタの大きさのもので最初の1つだけがUに入ります（引数が優先）。それ以外（`register char` を含む）は普通のローカル変数です。
- 大域変数と `static` 変数はY相対です。番地は、リンクマップのデータシンボル、またはセクションの基準（IDat/UDat）に `vsect` 内のオフセットを足して求めます。
- 変数はSからの相対番地で読まれるため、関数の各命令の時点でのSの深さを、リストの `pshs`・`puls`・`leas`・`,s++` から求めます。
  定数をインラインに置く `bsr _4` は2バイト積むだけとして扱い、自分でスタック上の引数を片付ける実行時ルーチン（`_lmove`）の分も差し引きます。
- 実行時には、求めた基準の「F+2の値が、この関数を呼ぶ命令の直後を指すか」を確かめます。合わない場合は近くの深さを探すので、
  スタックへの影響が分からない実行時ルーチンがあっても変数の位置を誤りません。呼び出し元のフレームもこの方法で順にたどります。
- `for`/`while` の増分・条件判定のコードはループ本体の後ろに出力されますが、ループの先頭行（`for`/`while` の行）に割り当てます。
  ループの直後の文にブレークポイントを置いても、ループの途中では止まりません。

対応していないもの：浮動小数点の値（16進で表示）、構造体の値渡しの引数とそれより後ろの引数、ビットフィールドの値、
`#define` の定数。大きさが分からない変数より後ろのローカル変数は「不明」と表示します。
`short` は `int` と同じ2バイトで、表示上も `int` です。

## エディタ（DAP / VS Code）

```sh
rs6809 ... --dap                 # 127.0.0.1:6810。--ice も有効になり、ブラウザUIと同時に使えます
rs6809 ... --dap 127.0.0.1:7000
```

エミュレータ自身がDAPサーバーです。各TCP接続が1つのセッションで、要求はHTTPと同じくエミュレータスレッドで処理します。
ブラウザで止めればエディタにも停止が通知され、その逆も同じです。

VS Codeでは `editors/vscode` の最小限の拡張（依存パッケージなし）を使います。

```sh
ln -s "$PWD/editors/vscode" ~/.vscode/extensions/rs6809.rs6809-debug-0.1.0   # VS Codeを再起動
```

`.vscode/launch.json`：

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "type": "rs6809",
      "request": "attach",
      "name": "rs6809: attach",
      "port": 6810,
      "symbols": ["${workspaceFolder}/artifacts/cdebug/hello"],
      "sourceDirs": ["${workspaceFolder}/examples"]
    }
  ]
}
```

| DAP | 内容 |
|---|---|
| `attach`（`launch` も同じ） | `symbols`・`sourceDirs` を読み込みます。`stopOnEntry` で一時停止します |
| `setBreakpoints` | ソース行。コードのない行は次のコードのある行へ移し、未ロードのモジュールは後で有効になったことを `breakpoint` イベントで通知します |
| `setFunctionBreakpoints` | シンボル名、または `$C000` |
| `setInstructionBreakpoints` | 逆アセンブル表示の番地 |
| `setExceptionBreakpoints` | 「OS-9 エラー復帰」「OS-9 プロセス切り替え」 |
| `stackTrace` | フレームの規則があればそれでたどり、なければスタック上の戻り番地（呼び出し命令の直後を指し、シンボルのある値）を探します。戻り番地は呼び出し命令の行を示します |
| `scopes`/`variables`/`setVariable` | Cのローカル変数・大域変数（展開・変更可）、レジスタ（変更可）、スタック32語、OS-9（プロセスID・モジュール・状態・直近のシステムコール） |
| `next`/`stepIn`/`stepOut` | 行単位。`granularity: "instruction"` で命令単位。行情報のない場所では命令単位 |
| `disassemble`/`readMemory`/`writeMemory` | CPU論理空間。逆アセンブルにはシンボルとソース位置を付けます |
| `evaluate` | Cの式（`s.x`、`p->next`、`arr[1]`、`*p`）、レジスタ名、シンボル、`$1234`、`[式]`（その番地の語）。デバッグコンソールで `>文字列` と入力するとゲストのコンソールへ1行送ります |
| `source`/`loadedSources` | ホストにないソースはリスト内の本文を返します |
| `output` イベント | ゲストのコンソール出力（ACIA 1）をデバッグコンソールに出します |

## OSの差し替え口

ICEの画面・HTTP API・DAPは、OS固有の処理を `osmon.rs` の `OsMonitor` トレイト経由でだけ使います。
2つ目のOSは、このトレイトを実装した型を `Ice::with_os` に渡せば載せられます（`Ice::new` はNitrOS-9）。

| メソッド | 内容 | NitrOS-9 |
|---|---|---|
| `detect` | メモリからOSを見分ける | `D.Init` が `Init` モジュールを指す |
| `info` | 名前・見出し・キュー名・メモリマップの種類・例外ブレークの名前（`/api/os/info`） | `OS-9`、`NitrOS-9 Level 2` など |
| `svc_at`・`svc_prefix`・`svc_mnemonic` | 命令がシステムコールか、番号・長さ・戻らないか。逆アセンブルの表記 | `SWI2`＋番号、`OS9 F$xxx` |
| `service_name` ほか | サービス・エラーの名前と説明 | `defs/os9.d` から生成した表 |
| `current`・`current_slot`・`pid_of`・`in_system` | 実行中のプロセスとそのID、システム状態か | `D.Proc`、`P$ID`、`P$State` |
| `describe_entry`・`describe_exit`・`error_of`・`learn` | 引数・結果の説明、エラーの判定、パス名の学習 | 下記 |
| `processes`・`summary` | プロセス表（共通の列＋OS固有の列）とキュー | プロセス記述子、`D.AProcQ` など |
| `images`・`image_calls` | ロード済みイメージと物理RAM上の範囲（シンボルの配置）、それが変わりうる呼び出し | モジュールディレクトリ、`F$Link` など |
| `memory_map`・`read_space` | メモリの使用状況、OSのアドレス空間 | `D.FMBM`／`D.BlkMap`、`sys`・`pidN` |

呼び出しの記録（呼び出しの木、内部呼び出しの集計、切り替えのタイムライン）は `osmon.rs` の `Tracer` で、OSに依存しません。
命令ごとの処理を軽くするため、システムコール命令の先頭バイト（`svc_prefix`）と、実行中プロセスの識別子の物理番地（`current_slot`）をOSから受け取ります。
プロセスIDは切り替えを検出したときだけ求めます。

画面のOSタブは `/api/os/info` の名前とキュー名で描き、プロセス表・モジュール・メモリマップはOS別の描画（`ui.html` の `OS_VIEWS`）を使います。
描画のないOSには、項目をそのまま並べる汎用の描画を使います。

## NitrOS-9の実装

### システムコールの捕捉

OS-9のサービス要求は `SWI2` の直後に1バイトの機能コードを置く形です（`OS9 F$Fork` = `10 3F 03`）。

1. 命令を実行する前に、PCの命令が `10 3F` なら呼び出しとして記録します。
   このとき呼び出し元の空間でレジスタと引数（パス名、書き込むデータ、モジュール名など）を読みます。
2. カーネルはスタック上のPCを機能コードの次へ進めてから `RTI` で戻ります。
   そこで「PC＝呼び出し位置+3、S＝呼び出し時と同じ、同じプロセス（`D.Proc` のID）」になった時点を復帰とみなし、
   出力レジスタとCCのキャリー（エラー）・Bのエラー番号を記録します。
3. 呼び出し時に同じプロセスの未完了の呼び出しがあれば、それを親とします。
   これにより、ユーザーの `I$ReadLn` の内部でドライバが行う `F$Sleep`、その中の `F$NProc` などを木構造で表示できます。
4. `F$Exit`・`F$Chain`・`F$NProc` は戻らない呼び出しとして扱います。ユーザー状態から新しい呼び出しが来た時点で、
   そのプロセスに残っていた未完了の呼び出しは破棄します（ユーザー状態のプロセスはカーネル呼び出しの途中にはないため）。
5. `I$Open`・`I$Create` の結果からパス番号とパス名の対応を学習し、`I$Dup`・`I$Close`・`F$Fork`（標準パスの継承）で更新します。
   以後の `I$Write` などは「パス1(stdout)」「パス3(echo)」のように表示されます。

システム状態（カーネル・ドライバ内部）の呼び出しは1秒に数十万回発生するため、レジスタの文字列化を表示時まで遅らせます。
ユーザー呼び出しとシステム呼び出しは別々に保持し（それぞれ最新15,000件・60,000件）、内部呼び出しが多くても
処理中のユーザー呼び出しが押し出されないようにしています。

### カーネル構造の読み取り

オフセットは参照キットの `defs/os9.d` に従います。サービス名・エラー名・`SS.xxx` は
同ファイルからLevel条件を評価して生成した `src/ice/tables.rs` を使います。

| 項目 | Level 1 | Level 2 |
|---|---|---|
| 判定 | `D.Init`($2A)が `Init` モジュールを指す | `D.Init`($24)が `Init` モジュールを指す |
| システム空間 | 64KB平坦 | ブロック0は物理0、その他は `D.SysDAT` のDATイメージ |
| 実行中プロセス | `D.Proc`($4B) | `D.Proc`($50) |
| キュー | `D.AProcQ`/`D.WProcQ`/`D.SProcQ`（$4D/$4F/$51） | 同（$52/$54/$56） |
| プロセス表 | `D.PrcDBT` のページ表、64バイト記述子 | `D.PrcDBT[ID]` が512バイト記述子の上位バイト |
| モジュール | `D.ModDir` の4バイト項目 | `D.ModDir`〜`D.ModEnd`($58)の8バイト項目、モジュールのDATイメージ経由で読む |
| メモリ | `D.FMBM` の256バイト単位ビットマップ | `D.BlkMap` の8KBブロックフラグ |

MulticompのLevel 1カーネルもMMUを有効（恒等マップ）にするため、MMUの状態ではなく `Init` モジュールの位置でLevelを判定します。

### 画面（OS-9モニタ）

- **スケジューラ**：`D.Proc` とアクティブ・待機・睡眠キュー。下のタイムラインは `D.Proc` の変化から求めた実行区間と、ユーザーのシステムコール（▲）です。
- **プロセス**：親子関係を木で表示し、`P$State` のフラグ（Sys・TSlp・TOut・Susp・Cond・Dead）、キュー、優先度、エージ、パス表、Level 2ではDATイメージを示します。
- **システムコール**：番号・プロセス・名前・引数・結果・所要サイクル。実行中の呼び出しは「実行中…」と表示します。
  行を選ぶと、そのプリミティブがカーネル内で何をするかの説明、入出力レジスタの差分、カーネル内部の呼び出しの木を表示します。
  そこから「この呼び出しで停止」「復帰で停止」を設定できます。
- **ブレーク条件**：特定のサービスの呼び出し前・復帰後、エラー復帰、プロセス切り替え、対象プロセスIDでの絞り込み。記録自体も切り替えられます。
- **モジュールディレクトリ**、**メモリマップ**（モジュール・プロセス記述子・使用中・空きを色分け）。

## 使い方の例

`echo hello` を実行すると、システムコールの一覧に次の流れが現れます（Level 1、プロセス2がShell）。

```text
P2 F$PrsNam   "echo"                 → 長さB=4
P2 F$Link     X→"echo"               → エラー E$MNF   メモリにないので
P2 I$Open     "echo"                 → パス番号A=3    実行ディレクトリのファイルを開き
P2 I$Read     パス3(echo) 最大13バイト → "\x87\xCD…"   モジュールヘッダを確認
P2 F$Load     X→"echo"               → ヘッダU=$B700  読み込んで登録
P2 F$Fork     モジュール"echo" パラメータ"hello\r" → 子プロセスID=3
P3 I$WritLn   パス1(stdout) 6バイト "hello\r"
P3 F$Exit     終了ステータスB=0       (戻らない)
P2 F$Wait     → 子3が終了 ステータス0
```

- `F$Fork` の呼び出しで停止させ、ステップオーバーするとプロセス3が作られ、スケジューラ表示とプロセス表が変わる様子を確認できます。
- 「エラーで復帰したら停止」を有効にして `echo hi` を実行すると、まずShellの `F$PrsNam` が名前の終わりで `E$BNam` を返した直後に止まります。
  再開すると、メモリにない `echo` の `F$Link` が `E$MNF` を返した直後に止まります。OS-9ではエラー復帰も通常の制御の流れであることがわかります。
- 「ユーザー呼び出しのみ」を外すと、`I$ReadLn` の待ち時間にドライバが `F$Sleep` を繰り返し、カーネルが `F$NProc` で
  次のプロセスへ切り替え、時計割り込みで `F$AProc` によりアクティブキューへ戻す様子が見えます。
- 速度を1MHz（実機相当）以下にすると、タイムラインでプロセスの切り替えを目で追えます。

## HTTP API

すべて `127.0.0.1` 上のJSONです。数値の既定は10進、アドレスは16進です（`$`・`0x` も可）。

| パス | 内容 |
|---|---|
| `GET /api/state` | 実行状態、停止理由、レジスタ、MMU、ブレーク設定、OS-9の要約 |
| `POST /api/run` `pause` `step?n=` `over` `out` `runto?addr=` `speed?hz=` | 実行制御 |
| `POST /api/reg?name=&val=` | レジスタ変更 |
| `POST /api/bp?addr=&op=add\|del\|toggle\|clear` | ブレークポイント |
| `POST /api/watch?addr=&len=&kind=r\|w\|rw`、`op=del&index=`、`op=clear` | ウォッチポイント |
| `GET /api/disasm?addr=&n=&back=` | 逆アセンブル（`back` で手前の命令境界から） |
| `GET /api/mem?addr=&len=&space=cpu\|sys\|phys\|pidN`、`POST ...&val=16進` | メモリ |
| `GET /api/trace?n=` | 実行トレース |
| `GET /api/console?since=`、`POST /api/console`（本文をACIA 1へ） | コンソール |
| `POST /api/os/break?code=&when=call\|return&op=del`、`errors=` `switch=` `pid=` `trace=` | OSのブレーク条件（`state` の `osbreak`） |
| `GET /api/os/info` | OSの名前・見出し・キュー名など（`OsMonitor::info`） |
| `GET /api/os/procs` `modules` `memmap` `services` | OSの構造（`state` の `os` に要約） |
| `GET /api/os/calls?since=&user=1&pid=&parent=&limit=` | システムコール（`since` は更新番号） |
| `GET /api/symbols`、`POST ...?path=`・`dir=`・`op=clear` | シンボル表の一覧・読み込み・ソース検索ディレクトリ |
| `POST /api/bp?sym=名前\|ファイル:行`、`symdel=ID` | シンボル・ソース行のブレークポイント（`state` の `symBreakpoints`） |
| `GET /api/resolve?expr=` | シンボル名・16進の番地を解決 |
| `GET /api/stack?n=` | スタックの語・戻り番地の判定・ラベル、呼び出しの連鎖 |
| `GET /api/vars?frame=` | フレームの一覧と、そのフレームの変数・大域変数（型・値・番地・1段の展開） |
| `GET /api/source?table=&src=` | 読み込んだソースの本文 |

テストやスクリプトからは `Ice::command("GET", "/api/state", b"")` で同じAPIを直接呼べます。

## 制約と注意

- Level 2のモジュールのアドレス（`MD$MPtr`）はモジュールのDATイメージ内の位置です。画面では物理アドレスに換算して表示し、元の値はツールチップに出します。
- Level 2の `P$UTicks` などのカウンタは、このカーネルが更新しないため表示しません（システムプロセスでは同じ位置にスタックの内容が残ります）。
- Level 2のタスク番号はプロセスが動いている間だけ割り当てられます。待機中・睡眠中のプロセスは0（未割り当て）です。
- 停止した時点が `F$NProc` の途中だと、実行待ちのプロセスがどのキューにも載っていないことがあります。
  決まった時点で見るには、OS-9ブレーク条件（呼び出し・復帰）で止めてください。
- 記録を有効にしたシェル待機中で約140MHz相当です（`tests/os_snapshot.rs` の `ice_speed`、命令実行のみでHTTPの処理を含まない値。ホストにより異なります）。実機の数十倍の速度です。
- ウォッチポイントはCPU論理アドレスで判定します。Level 2で別プロセスの同じ論理アドレスにも反応します。プロセスIDでの絞り込みはOS-9ブレーク条件のみです。
- 待ち受けは既定でlocalhostのみ、認証はありません。外部に公開しないでください。
- 停止中もタイマーは進みません（命令単位で時計を進めるため）。ステップ実行中に時計割り込みが入るのは正しい動作です。
- 戻り番地の判定は経験則です（直前の2〜4バイトが `JSR`/`BSR`/`LBSR` として解釈できる値）。シンボルを読み込んでいる場合は、
  シンボルのある範囲を指す値だけをスタックフレームにします。データがたまたま条件を満たすこともあります。
- 同じ名前のモジュールが複数あるときは、そのすべてに配置します。モジュールの中身がリストと一致するかは確かめていません。
  ソースを変更したら `c-debug-build.py` を実行し直してください。
- DAPにも認証はありません。待ち受けは既定でlocalhostです。
