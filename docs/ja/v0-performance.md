# 第0版（v0）の性能基準とボトルネック

2026-10-31 JSTの状態を第0版として保存した。これは比較用の版名で、Cargoのpackage versionは0.1.0のまま。
この調査でCPU・メモリ・周辺機器の実装は変更していない。

## 保存した基準

`artifacts/baselines/v0/` に調査前のソースアーカイブ、release実行ファイル、全ソースと入力のSHA-256、
7回のベンチマーク、perfの生データ・関数別レポート・メモリ読み取りの逆アセンブルを保存した。
この作業ディレクトリはGitリポジトリ未初期化のため、Gitタグではなくアーカイブとハッシュで固定している。
小さな結果・ハッシュ一覧は `docs/v0-baseline.json` にも保存している。

| 条件 | 値 |
|---|---|
| ホストCPU | AMD Ryzen 9 9900X |
| 環境 | WSL2 / Linux 6.6.87.2-microsoft-standard-WSL2 |
| Rust | rustc 1.99.1、既定のrelease設定 |
| 負荷 | NitrOS-9上でMicroware Cを使ってコンパイルしたマンデルブロー、76×25文字・48反復 |
| 計測区間 | 描画開始バナー末尾から完了マーカー末尾まで。OS・文字出力・タイマー処理を含む |
| 描画の仮想サイクル数 | 490,703,662 |
| 7回の描画時間 | 1.478108〜1.516325秒 |
| 中央値 | **1.481785秒、331.2MHz相当** |

1回ウォームアップした後の7回を使用。全回で出力のSHA-256、描画サイクル数、総サイクル数が一致した。
出力は端末へ表示せずパイプで回収した。端末への実表示を含むデモと時間が多少変わる。
コンパイル込みの総サイクル数は563,528,763だが、描画時間の中央値にはコンパイルを含めない。

## 実測したホスト側の内訳

perfの `cpu-clock:u`、997Hz、1775サンプル、lost samples=0。
以下は先頭0.5秒を除いて起動・コンパイルを避けた描画後半の**自己時間**の割合。
呼び出し先を含む累積時間ではないため、重複加算していない。1回のサンプリングなので割合は概数。

| 処理 | 自己時間の割合 | 対応する実装 |
|---|---:|---|
| メモリ読み取り | 34.4% | `Machine::read` |
| CPU命令処理 | 18.4% | `Cpu::step`、インライン展開された `execute` を含む |
| インデックス付きアドレス計算 | 14.1% | `Cpu::index` |
| 1命令ごとのマシン制御 | 9.4% | `Machine::step` |
| メモリ書き込み | 5.8% | `Machine::write` |
| 単項演算 | 4.1% | `Cpu::unary` |
| 割り込み受付の判定 | 4.1% | `Cpu::interrupt` |
| その他の実効アドレス計算 | 3.5% | `Cpu::ea` |
| CLIループ等 | 3.3% | `main`、インライン展開された `run` を含む |

全実行区間でも読み取り34.4%、CPU命令処理19.7%、index13.2%と、同じ順序だった。
画面出力・ファイルI/O・ホストのメモリ帯域不足が主因だとする証拠はない。
CLIの毎命令のディスクエラー確認などにも改善余地はあるが、今回の優先順位は低い。

## 改善する順番

### 1. 通常RAMへのアクセス経路

読み書きで約40%。読み取りは命令フェッチ・オペランド・スタックすべてから呼ばれる。
現在は普通のRAMを読むだけでも、ACIA status/data、タイマー、ROM有無、I/O範囲、ROM有効フラグ、
MMU有効フラグ、固定上位RAM、バンク番号と範囲を順に判定する。
逆アセンブルでもMMUやI/Oの判定を毎回実行しており、読み取り関数自体が最も多くサンプルされた。

候補は通常RAM用の短い経路と、MMU変更時に再計算する変換表。
特殊なI/Oページ・ROM・未搭載バンク・書き込み保護は従来と同じ動作を保つ必要がある。
NitrOS-9起動後もMMUを使うため、単にMMUを無視してRAM配列を読む変更はできない。

実測34%は「34%すべて削除できる」の意味ではない。
例えば読み取りの自己時間だけを半分にできた場合、他が同じなら全体は約1.21倍になる計算。

### 2. アドレス計算と命令処理

`index` と `ea` の自己時間だけで約17.6%。Cの生成コードはスタックやレジスタ相対アクセスが多い。
`index` はX/Y/U/Sの選択に汎用 `reg`/`set_reg` を使い、postbyteの解釈も毎回行う。
よく使う形式の短い経路、レジスタ選択の簡略化、関数呼び出し境界の削減を比較する。

CPU命令処理そのものも約18%。命令デコードの構造変更は候補だが、関数ポインタ表などが必ず速いとは限らない。
LTO・codegen-units・インライン指定も、コードサイズと速度を見ながら別々に実験する。

### 3. 命令ごとの割り込み・タイマー確認

`Machine::step` と `interrupt` で約13.4%。通常は割り込みがない命令でも関数を呼んで判定している。
割り込みなしの場合の短い経路や、次のタイマー期限を使った実行ループを比較する。
割り込み・SYNC/CWAI・ACIA入力の受付時点は保存し、無条件にまとめて後回しにはしない。

### 比較対象を固定する

ゲストのCプログラムを高速化すれば描画は速くなるが、エミュレータの改善とは区別する。
ここではCソース、生成コード、ROM、ディスク、スクリプトを固定する。
最適化ごとに同じ出力・同じ仮想サイクル数を確認し、ホスト時間が減ったかを測る。

## 再計測

第0版の保存済み実行ファイル：

```sh
python3 scripts/benchmark-emulator.py --workload fixed \
  --binary artifacts/baselines/v0/rs6809 \
  --output artifacts/benchmark/v0-repeat.json
```

変更後の実行ファイル：

```sh
cargo build --release
python3 scripts/benchmark-emulator.py --workload fixed --output artifacts/benchmark/candidate.json
cargo test --release -- --include-ignored
```

ベンチマークスクリプトはディスクや実行ファイルを再構築しない。
既定でウォームアップ1回＋計測7回、出力とサイクル数の決定性を確認してJSONを保存する。
異なる版を比較するときはJSON内の入力ハッシュも照合する。
端末・ホスト負荷・ビルド設定を揃え、各候補を1つずつ変更して比較する。

このWSL環境では `/usr/bin/perf` のラッパーが対応カーネル用実行ファイルを見つけないため、
実際に利用できる `/usr/lib/linux-tools/6.8.0-147-generic/perf` を直接使用した。
保存したデータは以下で再表示できる。

```sh
/usr/lib/linux-tools/6.8.0-147-generic/perf report \
  --stdio --no-children -g none \
  -i artifacts/baselines/v0/perf.data | c++filt -s rust
```

サンプルの落ちた命令位置から、個々の比較命令の正確な時間やキャッシュミス原因までは断定しない。
また、これはマンデルブローでの結果であり、I/O中心の別プログラムでは割合が変わる。
