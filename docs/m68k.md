# 68000 CPU core

`src/m68k/` is an instruction-level interpreter for the Motorola 68000. It runs separately from the 6809 core (`src/cpu.rs`) and uses no external crates.
The ICE uses it with `--cpu 68000` (see "Swapping the CPU" in [ICE](ice.md)).

## Usage

```rust
use rs6809::m68k::{Bus68k, M68k};

struct Ram(Vec<u8>);
impl Bus68k for Ram {
    fn read8(&mut self, a: u32) -> u8 { self.0[a as usize] }
    fn write8(&mut self, a: u32, v: u8) { self.0[a as usize] = v }
}

let mut cpu = M68k::default();
cpu.reset(&mut ram);          // reads SSP and PC from vectors 0 and 1
loop { cpu.step(&mut ram); }  // one instruction (or taking an interrupt)
```

- **Bus**: `Bus68k` reads and writes bytes at 24-bit addresses; word accesses default to two byte accesses.
  Word and long accesses at odd addresses never reach the bus; the CPU turns them into address errors.
- **Registers**: `d[0..8]`, `a[0..8]` (`a[7]` is the active stack pointer), `sr`, `pc`.
  The inactive stack pointer is read and written with `usp()`, `ssp()`, `set_usp` and `set_ssp`.
  `set_sr` switches the stack pointer when the S bit changes.
- **Interrupts**: the machine sets `irq` (0–7) and, if needed, `irq_vector` (a vector number).
  When `irq_vector` is `None`, the autovector (24 + level) is used. Level 7 is non-maskable.
- **Other**: `stopped` is set during `STOP`, `halted` on a double fault, and `reset_out` by the `RESET` instruction. `cycles` is the running cycle count.

## The plain machine (`--cpu 68000`)

`m68k::machine::Sim68k` is the smallest machine for running a program and examining it in the ICE (the real board's layout is chosen in stage 3).

| Address | Contents |
|---|---|
| `$000000`– | RAM (1 MiB by default, up to 16320 KiB with `--ram-kb`). The vectors are at address 0 too |
| `$FF0000` | Console status: bit 0 = byte received, bit 1 = ready to send (always 1) |
| `$FF0001` | Console data: reading gets the received byte, writing sends one |

Other addresses read `$FF` and ignore writes. There are no interrupts and no bus errors.

```sh
rs6809 --cpu 68000 --bin prog.s68 --until "done"     # standard input/output is the console
rs6809 --cpu 68000 --bin prog.bin --load 0x1000      # raw images start at the load address
```

`--bin` reads a Motorola S-record (S1/S2/S3, start address from S7/S8/S9) if the file starts with `S` and a digit, and raw data otherwise.
The start address is `--pc`, else the S-record's start address, else the load address; the SSP is the top of RAM, and both are written to vectors 0 and 1.
A raw image loaded at address 0 without `--pc` uses its own reset vectors. A double fault ends the run.

## The Tiny68K-compatible machine (`--machine tiny68k`)

`m68k::tiny68k::Tiny68k` reproduces Bill Shen's Tiny68K board as far as FUZIX and EtchedPixels' EmulatorKit see it.
It is used for CP/M-68K ([CP/M-68K](cpm68k.md)) and FUZIX ([FUZIX/68000](fuzix68k.md)).

| Address | Device |
|---|---|
| `$000000`–`$FF7FFF` | RAM (16 MiB less the top 32 KiB) |
| `$FFE000`–`$FFEFFF` | IDE (CF). The register is (address & 31) >> 1. The data register is 16 bits wide, and the first byte of a sector is the low byte of the word (the bytes are swapped) |
| `$FFF000`–`$FFF01F` | MC68681 DUART. Odd addresses; the register is (address >> 1) & 15. Channel A is the console, B the auxiliary port |

- The DUART interrupts at level 2 with the vector in IVR. It raises receive-ready (RxRDY) and counter/timer (X1 = 3.6864 MHz) interrupts.
  The timer advances with the CPU's cycle count, taking the CPU as 10 MHz (as EmulatorKit does).
- The IDE answers LBA `READ SECTORS`, `WRITE SECTORS` and `IDENTIFY DEVICE`. Commands finish at once (no waiting on BSY).
  There is no drive 1 (slave); with the DEV bit set the status reads 0.
  The `--disk` image is read into memory; `--persist-disk` also writes changes back to the file.
- `--tty2 [127.0.0.1:6812]` listens for TCP on DUART channel B (for telnet: it asks for character mode and remote echo, and drops telnet commands).
- The state file (the ICE's "Save", `--load-state`) is `RS68KST1` followed by the CPU (D0–D7, A0–A7, the inactive SP, SR, PC, cycle count, STOP, halt),
  the machine kind, RAM, the DUART (both channels' mode registers, pending input, ACR, IMR, timer), the IDE (registers, the transfer buffer)
  and, if needed, the disk contents, laid out as fixed-width big-endian integers and length-prefixed byte strings (`src/m68k/state.rs`).
- When the CPU waits in `STOP` and nothing is pending, it skips ahead to the next timer event (or scheduled input) without running instructions.
  In the ICE and interactive runs, the host sleeps for that time in real time, so an idle guest uses almost no host CPU and its clock keeps real time
  (batch runs with `--until` or `--max-cycles`, and tests, just skip ahead without sleeping).
- There is no monitor ROM. The machine starts at `--pc` in supervisor mode with SSP = top of RAM.
  `--boot-sector`, like the monitor's boot command, places LBA 1 of the disk at `$15000` (swapping the bytes of each word) and starts there.

## What is implemented

- Every 68000 instruction (including `MOVEP`, BCD arithmetic, `MOVEM`, `CHK`, `TAS`), line A, line F and `ILLEGAL`.
- Exceptions: address error (14-byte frame), illegal instruction, privilege violation, divide by zero, `CHK`, `TRAPV`, trace, `TRAP` and interrupts.
- Cycle counts are per instruction: the tables in chapter 8 of the MC68000 User's Manual (base time plus effective address time),
  with division following Jorge Cwik's analysis of the microcode.
- Bus error (`BERR`) input and the prefetch queue are not modelled. PC points at the next instruction word to be read.

## Address errors

On an address error the 68000 stacks the faulting access's address, the instruction register, SR, a status word and the PC at that moment.
The stacked PC and the cycle count depend on how far the instruction had got (extension word reads and prefetches).
The following rules were read from the SingleStepTests data and implemented.

| Item | Rule |
|---|---|
| Status word | `(IR & $FFE0) \| R/W<<4 \| I/N<<3 \| FC`. I/N is 1 for program (instruction) accesses. FC is the function code of the faulting access (the mode before entering the exception) |
| Stacked PC | The PC at the fault − 2. For branches to odd addresses (`JMP`, `JSR`, `Bcc`, `BSR`, `DBcc`, `RTS`, `RTE`, `RTR`), the target − 4 |
| Cycles | 50 + the cycles used up to the fault (4 per extension word read, 2 of internal time for `-(An)` and indexed addresses, 4 per read or write / 8 for longs). For branches, the instruction's normal time − 8 |
| Long addresses | Long writes to `-(An)` and `ADDX`/`SUBX -(An)` reads access the low word first, so address + 2 is reported |
| Particular cases | `JSR` checks the target before pushing the return address (`BSR` after pushing). If `MOVE` writes to `(An)+`, `An` is not incremented on failure. With `-(An)` the next instruction is prefetched before the write (PC + 2, cycles + 4, and for longs `An` decremented by only 2). With `(xxx).L` a move from memory writes before reading the second word of the address. `MOVEM (An)+` has advanced by one word. `ADDX`/`SUBX.l -(An)` has decremented by 2 |

## Verification

```sh
python3 scripts/fetch-68000-tests.py                               # once (about 250 MB)
cargo test --release --test m68k_sst -- --ignored --nocapture     # instruction tests and the disassembler
cargo test --release --test m68k_core                              # interrupts, STOP, trace and more
```

[SingleStepTests/680x0](https://github.com/SingleStepTests/680x0) (v1, commit `e0d5ece`) has 125 files with about a million per-instruction tests.
It carries no license notice, so it is not included in the repository; the fetch script downloads it and converts it to a binary format (`artifacts/sst68000/`).
Each test runs one instruction and compares the registers, SR, PC, RAM and cycle count. The prefetch state and the order of bus accesses are not compared.

| Group | Tests | Matching |
|---|---|---|
| Not address errors | 821,970 | all (except the 3 below) |
| Address errors | 178,087 | all (whole frame, registers and cycle counts) |

The 3 excluded tests:

- `ASL.b Q, D2` numbers 1583 and 1761: errors in the data (upstream issue #4). Our results match the correct values given in the issue.
- `DIVU (d16, A7), D0` number 5745: the only divide by zero in the whole data set, and it stacks the instruction's start address.
  The manual stacks the next instruction's address, and thousands of `CHK` and `TRAPV` tests do so too, so we follow the manual.

Behaviour the test data does not cover (reset; interrupt masking, autovectors, given vectors and level 7; `STOP`; trace; privilege violations;
`ILLEGAL` and lines A/F; the `RESET` instruction; `TRAP` and `RTE`) is checked in `tests/m68k_core.rs`.

The disassembler (`m68k::disasm`) is checked against every instruction test (1,000,060 of them): the instruction kind and size match the file name,
and for non-branching instructions the instruction length matches how far PC advanced.

## Research for the machine layout

- FUZIX's Tiny68K boot loader (`Kernel/platform/platform-tiny68k/loader.S`) is called by the monitor ROM's "CP/M boot loader",
  but then works without the monitor, driving the 68681 DUART (`$FFF000`) and the IDE directly.
  If the emulator loads the disk's boot loader into memory and starts it, booting should work without a monitor ROM.
- The Tiny68K monitor ROM (`T68kbug_r07.BIN` and others) is distributed on retrobrewcomputers.org,
  but a Cloudflare check page prevents fetching it automatically, and its distribution terms could not be confirmed.
